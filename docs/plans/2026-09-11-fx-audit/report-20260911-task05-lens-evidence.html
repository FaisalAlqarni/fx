Does the pipeline lens find what a careful reader misses?

Task 05 of the fx-audit plan, 2026-09-11. Evidence for one decision, gathered before the decision is asked.

The plan says fx-lens-pipeline ships only if it finds what a control reviewer misses. The lens was written, and a fixture of queue and worker code was seeded with eight defects, one per hunt group. Both arms read the same stripped fixture, where no comment names a defect, and were scored against a separate key that neither could see.

What the counts do and do not show

  • On the key, the lens adds one group: fairness. It is also the only group that needs knowledge of how queues behave under load. The other seven yield to ordinary questions: is this released on every path, what happens if this throws, can this retry forever.
  • The lens is tighter. 13 findings ranked by severity, each stating its production consequence, against 43 from the control. It ceded two items to the database lens and noted nothing for the silent-failure lens, as its brief requires.
  • It read code, not labels. For groups 6 and 7 it reached the mechanisms the key corrected, a lost acknowledgment and a retry that runs forever, rather than the wrong ones the original task file stated and which it could no longer see.
  • The unseeded bug is not an advantage. Both arms caught it. An earlier ledger line implied otherwise and has been corrected.

Two reasons to distrust these numbers

  • One sample per arm. The repository's own skill-testing reference asks for five per variant, because single runs vary.
  • The control may be stronger than reality. It was one unhurried top-tier read aimed only at this file. Without this lens, a real fx-review branch run gets a correctness pass, a standards pass, a spec pass and an unprimed adversarial pass, each with its own focus. Whether those catch fairness is the question that actually matters, and nobody has measured it.

The decision, and its options

The design chose a separate lens over folding this material into fx-lens-database, which ADR 0008 had recommended to avoid a second dispatch. The reason, recorded for ADR 0014, was structural: the database lens triggers on schema and queries, so it would not fire on a diff that only touches a worker or a queue config. This evidence does not touch that reason. It does say most of the lens's hunt list overlaps what other review passes already catch.

A. Narrow the lens to what only it finds, then re-measure recommended

Keep the separate lens and its triggers, so the structural reason survives. Cut the hunt list down to concerns that need pipeline knowledge: fairness across tenants, rate limits enforced per process in a multi-process deployment, delivery guarantees reasoned about under crash and redelivery, poison messages, visibility timeouts shorter than processing time, retry storms during an outage. Re-seed the fixture with defects of that shape and run both arms again.

Cost: one more implementer round on task 05, and the lens loses breadth it currently duplicates.

B. Keep the lens as designed

Accept a one-group lead on the key plus a tighter report as enough, and amend the task's criterion so it no longer demands a differential this fixture cannot supply.

Cost: a second dispatch on every matching branch whose findings mostly repeat other passes, which is the habit ADR 0008 warned trains readers to skim lens output.

C. Fold it into the database lens

ADR 0008's original recommendation. One dispatch instead of two.

Cost: the pipeline material stops firing on worker and queue diffs, which is the gap this lens was built to close.

D. Measure properly before choosing

Five runs per arm, with the control replaced by the passes fx-review actually dispatches without this lens. This combines with any of A, B or C.

Cost: roughly ten to twenty further agent runs. Offered, not started.
