# fx judge hooks: shell guard, Stop evidence check, stuck-loop nudges

**Date:** 2026-10-22
**Status:** ready-for-agent
**Approved:** 2026-10-22
**Glossary:** none (fx has no `CONTEXT.md`); the terms below are defined in this file

## Problem Statement

fx tells agents to show evidence before claiming work is done, to stop and debug instead of retrying, and it guards irreversible git commands. Everything outside git rests on instruction alone. An agent can still run `rm -rf ~`, pipe a download into a shell, end a turn that edited ten files without running a single test and call it finished, or run the same failing command five times in a row. Nothing on any of the four harnesses notices.

Small local decision models now speak one wire protocol (`POST /v1/systemone`, the TypeSafe Jev API) and answer a typed question in tens of milliseconds on a home GPU. The owner measured them on real fx session commands (`/development/promots/jev-research.md` section 9). They can settle the grey cases plain code cannot, but they are wrong often enough that they must never be the only line, must never stall a session, and must never send anything off the machine unless the user asked for that.

This is sub-project 2 of 4. It requires sub-project 1 (`docs/plans/2026-10-22-ts-migration/`) complete: every fx source is TypeScript under `src/`, compiled to committed JavaScript at the runtime paths.

## Solution

Four parts, one design, on Claude Code, Codex, opencode 1.x and opencode 2.x, on Windows, macOS and Linux:

1. **A shared judge client.** Any `/v1/systemone` server, named in one per-machine config file by base URL, model id and an optional key. No file means no judge, and every hook then runs on plain code alone. Secrets are redacted before anything is sent, every call has a hard 1.5 s budget, and an unsure answer comes back marked as such.
2. **A shell guard** on PreToolUse, shell commands only. Hard denial rules first, then a read-only allowlist, then the judge for grey cases with one choice question (run, ask, deny). An unsure judge means ask. A logged override stamp, honoured only after a later user prompt, softens a judged deny to ask.
3. **A Stop evidence check** on Stop and SubagentStop. A turn that edited files and shows no passing check since the last edit is blocked once, with the reason. The judge may lift the block when the final message does not claim the work is verified.
4. **A stuck-loop tracker** on PostToolUse, plain code only. Three signals (a command failing three times, twelve reads in a row with no edit, ten edits with no check) each inject one short line pointing at fx-debug. It never blocks.

Every decision is on from day one and every judged decision is logged locally for later threshold calibration. A judge that is configured but down costs nothing but a SessionStart line.

## User Stories

1. As an fx user on a fresh install, I want every new hook to work with no judge configured, so that fx adds protection without asking me to install a model.
2. As an fx user, I want catastrophic shell commands (wiping a home or root directory, formatting a disk, piping a download into a shell) refused on every harness before they run, so that one bad command cannot destroy my machine.
3. As an fx user, I want read-only commands (`ls`, `git status`, `grep`) to run with no judge call and no delay, so that the guard costs nothing on the common case.
4. As an fx user with a judge configured, I want a grey command (one that is neither plainly destructive nor plainly read-only) judged as run, ask or deny, so that the guard catches what a regex cannot.
5. As an fx user, I want a judge that is unsure to ask me rather than decide, so that a weak model never silently allows or refuses.
6. As an fx user on Claude Code, I want "ask" to reach me as the harness's own permission prompt, so that I decide.
7. As an fx user on Codex, which has no ask decision, I want "ask" to run the command with a visible warning, so that Codex never fails the hook run and I still see what happened.
8. As an fx user on opencode 2.x, I want "ask" to use opencode's own ask effect, and on opencode 1.x, which has no ask, I want the call refused with an instruction to confirm with me and re-run with the override stamp.
   *Amended by ledger ruling (noted 2026-10-23; state.md, the task 06 and task 07 stamp rulings and the opencode texts ruling):* no stamp is honoured on either opencode major, so the 1.x refusal says fx cannot take the user's agreement there and the user can run the command themselves; opencode 2.x runs the code rules only, with no judge, so its guard never asks (`references/harnesses/opencode-v2.md`).
9. As an fx user, I want only my own prompts to make the judge more lenient, never text that came from a tool result or a dispatch prompt, so that a hostile web page or file cannot talk the guard into allowing a command.
10. As an agent whose command the judge denied or asked about, I want to add `# fx-ok: <reason>` to the command after the user confirmed in a new prompt, so that the decision moves to the user (ask, or a visible warning where the harness has no ask), and I want that reason logged; a stamp with no user prompt since the refusal is ignored.
    *Amended by ledger ruling (noted 2026-10-23; state.md, the task 06 and task 07 stamp rulings and the opencode texts ruling):* the stamp works on Claude Code (ask) and Codex (warning) only; on opencode 1.x and 2.x no stamp is honoured, so there is no stamp warning on opencode 1.x, and the refusal says the user can run the command themselves.
11. As an fx user, I want a command the judge denied in the last ten minutes, when retried, to come to me as an ask where the harness has one (and stay denied where it does not), so that a retry loop ends with my decision and never with a silent allow.
12. As an fx user, I want the judge to have a hard 1.5 s budget and to fail open, so that a slow or dead judge never stalls a session.
13. As an fx user with a judge configured, I want one line at session start when the judge cannot be reached or its config is invalid, and silence otherwise, so that I know when I am running on plain code alone.
14. As an fx user, I want nothing sent off my machine unless I configured a remote judge, and secrets redacted before anything is sent even to a local one, so that the guard never leaks.
15. As an fx user, I want every judged decision, hard denial, override and Stop block logged as one JSON line on my machine, so that thresholds can be calibrated later on real data.
16. As an fx user, I want a turn that edited files and ran no passing check since the last edit to be stopped once with "run a check", so that "done" means verified.
17. As an fx user, I want that Stop block never to fire twice in one turn, so that an agent that cannot run a check is not trapped.
18. As an fx user, I want a check counted as evidence when it is one of my repo's `.fx.json` check commands that succeeded, or when any command's output shows a test runner's own pass summary, so that the check knows what testing means here.
19. As an fx user with a judge, I want the Stop block lifted when the final message plainly does not claim the work is verified, so that an honest "I could not run the tests" is not blocked.
20. As an fx user, I want a turn that edited only documentation files exempt from the Stop check, so that writing a plan is not blocked for lacking tests.
21. As an fx user on opencode, where a Stop hook cannot block, I want the missing-evidence reason delivered as a reminder at the start of the next request, so that the agent still hears it.
22. As an fx user, I want one short line pointing at fx-debug when the agent runs the same failing command three times, reads twelve times in a row without editing, or edits ten times without a check, so that a stuck agent changes approach.
23. As an fx user, I want each nudge at most once per turn and never a block, so that the tracker cannot get in the way.
24. As a repo owner, I want to switch the shell guard's judge step, the Stop check or the nudges off for one repo in `.fx.json`, while the hard rules and the allowlist always run, so that a repo with unusual needs can opt out without a hostile repository or an agent being able to turn the hard rules off.
25. As an fx user, I want fx-setup to explain the judge options and write the config file for me, with a local recommendation per OS, so that setting up a judge takes one guided step.
26. As the fx author, I want a fake `/v1/systemone` server and a mock backend for tests, so that every judge path is tested offline.
27. As the fx author, I want each hook tested as a process (stdin payload in, stdout and exit code out), so that the tests see what a harness sees.
28. As the fx author, I want the projects these ideas came from credited in a notices file, so that their authors get credit for the designs fx rewrote.

## Implementation Decisions

**1. Judge config, one file per machine.** The config lives at a per-OS user config path: on Linux and macOS `$XDG_CONFIG_HOME/fx/judge.json`, else `~/.config/fx/judge.json` (macOS follows the same CLI convention opencode already uses there); on Windows `%APPDATA%\fx\judge.json`. Its fields: `base_url` (string, the prefix before `/v1/systemone`, or the literal `mock`), `model` (string, a pinned model id), `api_key` (optional string). `mock_answers` (object, question name to answer) is read only when `base_url` is `mock`. No file means no judge and is not an error. A file that does not parse, or lacks `base_url` or `model`, means no judge plus a health problem (decision 9). A `base_url` with userinfo (`user:pass@`) is rejected. Only a loopback address (`localhost`, `127.0.0.0/8`, `::1`) counts as local; every other address, private networks included, is remote: data sent there leaves the machine, `fx-setup` and `judge-cli write` say so, and plain `http` to it is rejected unless the file sets `insecure_http: true` (an explicit opt-in, because a Bearer key would travel in clear text). A rejected `base_url` is a health problem and no judge (red team I14). The config parser is a trust-boundary parser in sub-project 1's sense: input from `unknown`, typed result or typed failure, no casts. fx writes this file only through `fx-setup` (decision 11), with mode `0600` on POSIX.

**2. Judge client.** One module asks a list of named questions over one state in one `POST {base_url}/v1/systemone` call, using Node's built-in `fetch` with an abort after a hard budget of 1,500 ms (a constant; the caller cannot raise it). It sends `Authorization: Bearer <api_key>` only when a key is set. It parses the response from `unknown`. Question types used here: `choice` (options with descriptions, answer is `choice` plus `probabilities` per option) and `noul` (answer is a probability). The result is a tagged value:
- an answer per question, each carrying its raw probabilities and an `escalate` field: `null`, or a typed reason (`low-top`, `small-gap`, `mid-noul`);
- or `unavailable` with a typed reason (`no-config`, `bad-config`, `timeout`, `network`, `http-<status>`, `bad-response`).

The unsure rule for a choice answer: escalate `low-top` when the top probability is below 0.60, `small-gap` when the top minus the runner-up is below 0.20. For a noul answer: escalate `mid-noul` when the probability is between 0.30 and 0.70. Every threshold is a named constant in one module, and every log line carries the raw probabilities, so a recalibration never needs to re-run a model.

The `mock` backend answers from `mock_answers` with no network, for offline use and for tests that cannot run a server. Tests that exercise the network path use a fake `/v1/systemone` server (Testing Decisions).

Redaction runs on every string before it enters a request, a log line or a journal line: private key blocks; `Authorization` values of any scheme (`Bearer`, `Basic`, `Token`); header values whose name contains `key`, `token`, `secret`, `auth`, `cookie` or `session` (`-H "X-API-Key: v"`, `Cookie: a=b`); URL userinfo in any scheme (`https://u:p@`, `postgres://u:p@`); `KEY=value` and `--password value` style pairs whose name contains `key`, `token`, `secret`, `password` or `passwd`; password flags `curl -u user:pass`, `mysql -pSECRET`, `sshpass -p secret`, `docker login -p secret`; known token shapes (`sk-`, `ghp_`, `gho_`, `github_pat_`, `glpat-`, `npm_`, `xox[abp]-`, `AKIA`, `AIza`, JWTs `eyJ...`); and any unbroken base64 or hex run of 40 characters or more (red team I13). Each becomes `[REDACTED]`. Caps after redaction: command 2,000 characters, user prompt 1,500, final message 2,000.

Nothing leaves the machine unless the user configured a remote `base_url`. With no config, no network call is made at all.

**3. Per-machine state: decision log and session journal.** State lives at a per-OS path: on Linux and macOS `$XDG_STATE_HOME/fx`, else `~/.local/state/fx`; on Windows `%LOCALAPPDATA%\fx`. Two kinds of file:
- `decisions.jsonl`: one JSON line per logged decision (time, harness, event, session id, cwd, redacted command or message, source, action, judge model, probabilities, latency, escalate reason, override reason). Logged: every hard denial, every judged or no-judge grey decision, every override, every loop-guard repeat, every Stop block or lift, every nudge, every health problem. Not logged: allowlist allows and silent passes. When the file passes 5 MB it is renamed to `decisions.1.jsonl` (replacing any older one) before the next append. Files are created with mode `0600` on POSIX.
- `sessions/<key>.jsonl`: the session journal, one append-only JSON line per event (`prompt` with the redacted user text or `null` for a turn start that is not a user prompt, plus the agent type for a subagent's turn start; `tool` with kind, normalized command, outcome and whether it verified; `edit` with path; `deny` and `ask` with the normalized command the judge refused or asked about; `nudge`; `stop-block`). Every string is redacted before it is appended, and commands are stored in their redacted normalized form, which is also the form the loop guard and the stamp rule compare (red team I12). On Windows the `0600` mode does not apply; the files rely on the user profile's own permissions. Appending one short line is the only write, so parallel hook processes for parallel tool calls do not overwrite each other. Each line is capped at 2 KB (commands truncated to 500 characters in the journal). The key is the harness session id, with `__<agent_id>` appended for a subagent's own events. A payload with no session id gets no journal, and every stateful feature (loop guard, Stop check, nudges) skips it.

At SessionStart, journal files not modified for seven days are deleted. A read or write failure in either file never changes a decision: the hook proceeds as if the file were empty and the failure goes to stderr.

**4. The turn.** A turn is everything since the last `prompt` event in a journal. Claude Code and Codex record the prompt at `UserPromptSubmit` (new registrations on both). A subagent's turn starts at its `SubagentStart`, which both harnesses already route to fx. A `UserPromptSubmit` that carries an `agent_id` (Codex fires it inside spawned subagents, with the parent's dispatch text: `docs/plans/2026-09-21-multi-harness/research/codex.md`, Agent identity) is never a user prompt: it appends a `prompt` event with text `null` to the subagent's journal only and leaves the root turn alone (red team C3). A `UserPromptSubmit` whose text starts with `[fx] ` is fx's own Stop continuation and is ignored (red team I18). On opencode the next user prompt marks the boundary: opencode 1.x through its `chat.message` hook, opencode 2.x through `ctx.session.hook('prompt')`.

**5. Shell guard.** Runs on PreToolUse for shell calls only: Claude Code `Bash`; Codex `Bash` with a string `tool_input.command` (Codex's `exec_command` reaches hooks under that same name and shape: `docs/plans/2026-09-21-multi-harness/research/codex.md`, `tool_name` values; red team M21); opencode 1.x `bash`; opencode 2.x `shell`. It runs after the existing git guard and only when the git guard allows. Order:
1. **Hard denial rules**, matched per command at command position, never on the raw text (red team I4). The command is split with the git guard's own `stripHeredocs` and `splitSegments` (a heredoc body that no shell reads is data; `grep -rn shutdown src` and `git commit -m "handle reboot"` name a word, they do not run it), each segment's program is found past environment assignments and the wrappers `sudo`, `env`, `command`, `nice`, `nohup`, `time`, `timeout`, `exec`, and a shell's `-c` argument (`expandShellC`) is checked as a command of its own. The rules (red team I5 enumerates the spellings, task 03 holds the list): `rm` with any recursive flag (`-r`, `-R`, `--recursive`, alone or in a cluster, force optional) on `/`, `/*`, `~`, `~/`, `~/*`, `$HOME`, `${HOME}`, `$HOME/`, `$HOME/*` (quoted or not), `/home/<name>`, `/Users/<name>` (with or without `/` or `/*`), or a system directory (`/bin`, `/boot`, `/dev`, `/etc`, `/home`, `/lib`, `/lib64`, `/opt`, `/proc`, `/root`, `/sbin`, `/srv`, `/sys`, `/usr`, `/var`, `/Users`, `/System`, `/Library`, `/Applications`, `/private`, each with or without `/` or `/*`); `mkfs`; `dd` with `of=/dev/`; redirection into a block device; a fork bomb; `chmod -R` or `chown -R` on `/` or a home spelling; a download (`curl`, `wget`, `iwr`, `irm`, `Invoke-WebRequest`, `Invoke-RestMethod`) piped into a shell (`sh`, `bash`, `zsh`, `dash`, `iex`, `Invoke-Expression`, with or without `sudo`), fed to one by process substitution (`bash <(curl ...)`), or run as a shell's `-c` argument (`bash -c "$(curl ...)"`); `shutdown`, `reboot`, `halt`, `poweroff`; Windows `format <drive>:`, `Remove-Item -Recurse -Force` on a drive root, `~`, `$HOME` or `$env:USERPROFILE`, `rd /s /q` and `del /s /q` on a drive root or `%USERPROFILE%`. A hard denial is final: no judge, no stamp, no loop guard, no repo switch.
2. **Read-only allowlist**: one simple command whose program is on a fixed list, with a per-program flag denylist for flags that run code or write files (red team I6): `ls`, `pwd`, `cat`, `head`, `tail`, `wc`, `grep`, `rg` (not `--pre`, `--pre-glob`), `find` (not `-delete`, `-exec`, `-execdir`, `-ok`, `-okdir`, `-fprint`, `-fprint0`, `-fprintf`, `-fls`), `tree` (not `-o`), `stat`, `file`, `du`, `df`, `which`, `type`, `echo`, `date`, `whoami`, `uname`, `git` with no global option before the subcommand (any `-c`, `-C`, `--git-dir`, `--work-tree`, `--exec-path` or other option there makes it grey) and the subcommand `status`, `log`, `diff`, `show` (none with `--output` or `--ext-diff`), `branch` (none of `-d`, `-D`, `-m`, `-M`, `-c`, `-C`, `-f`, `-u`, `--delete`, `--move`, `--copy`, `--force`, `--set-upstream-to`, `--unset-upstream`, `--edit-description`), `rev-parse`, `ls-files`, `remote -v`, `blame`; `node --version`/`-v`, `npm ls`, and PowerShell `Get-ChildItem`, `Get-Content`, `Get-Location`, `dir`. A command that chains, pipes, redirects, substitutes or backgrounds (any of `;`, `&`, `|`, `>`, `<`, `` ` ``, `$(...)`, newline, anywhere in the text) never takes this shortcut. Nor does a command naming a secret path (`.env` and `.env.*`, `id_rsa`, `id_ed25519`, `id_ecdsa`, `id_dsa`, `.ssh/`, `.pem`, `.key`, `.p12`, `.pfx`, `credentials`, `.aws/`, `.kube/config`, `.docker/config.json`, `.git-credentials`, `.npmrc`, `.netrc`, `.pgpass`). The repo's own `.fx.json` `test_one`, `test_scope`, `test_all`, `lint` and `setup` commands are allowlisted too, by the matching rule of decision 7, but only when the part of the command after the matched text holds none of the chain, pipe, redirect or substitution characters above (red team I16). An allowlisted command runs silently and is not logged.
3. **The judge**, for every grey command, with one `choice` question named `decision` whose options are, in this order, `ask` ("the command could cause harm that is hard to undo, or its effect is unclear, and the user has not asked for it"), `run` ("the command is safe to run, or the user explicitly asked for exactly this"), `deny` ("the command is destructive, exfiltrates secrets, or acts outside the project, and the user did not ask for it"). The state holds the command with every unquoted `#` comment removed (the stamp included, so a comment cannot argue with the judge: red team I7) and then redacted, the working directory's base name, the harness, and the user's latest prompt in this session (decision 6). Policy: answer `run` and no escalation is allow; answer `deny` with top probability at least 0.80 and gap at least 0.40 is deny; any other answer, and any escalation, is ask.
4. **No judge or judge unavailable**: allow, logged with source `no-judge` or `judge-down` and the unavailable reason. Fail open. A repo whose `.fx.json` sets `hooks.shell_judge` to `false` skips step 3 the same way, logged with source `switched-off` (decision 10).

*Amended by ledger ruling (noted 2026-10-23; state.md, the task 06 and task 07 stamp rulings, the opencode texts ruling and task 07's code-only branch):* on opencode 1.x and 2.x no stamp is honoured, because opencode cannot tell the user's prompt from a parent agent's prompt to a child session; the opencode refusal texts drop the stamp advice. opencode 2.x runs steps 1 and 2 only (the code-only branch below). The opencode cells of the stamp paragraph and of the ask row in the table below are superseded.

**Override stamp (amended, red team C2, owner-approved 2026-10-22).** The owner's original decision let a `# fx-ok: <reason>` stamp skip the judge. The agent writes the stamp, and so can a prompt injection that tells it to, so the stamp is now gated on the user. A stamp (reason at least one non-space character) is honoured only when the root session's journal holds a `prompt` event after the most recent `deny` or `ask` event for the same normalized command; otherwise it is ignored and the judge decides as if it were absent. An honoured stamp never skips the judge and never skips an ask: the judge still runs, a `run` answer allows, and a `deny` or `ask` answer becomes ask on Claude Code and opencode 2.x, which have a native ask, and warn on Codex and opencode 1.x, which do not. It is logged with source `override` and the reason. It never touches a hard denial or the git guard. The stamp is a shell comment, so it works under bash, sh, zsh and PowerShell; `cmd.exe` has no inline comment and would pass it to the program as arguments, so it is not supported there (red team M27).

**Loop guard (amended, red team C2).** When the same normalized command (comments removed, trimmed, whitespace collapsed, redacted) was denied by the judge in this session within the last ten minutes, the repeat is not judged again. On Claude Code and opencode 2.x it becomes ask, so the user decides instead of a retry loop; on Codex and opencode 1.x it stays deny. It never becomes allow. It is logged with source `loop-guard`.

**Decisions and their harness forms.** The guard returns one of `allow`, `warn`, `ask`, `deny`, each with a reason that starts `[fx] `:

| Decision | Claude Code | Codex | opencode 1.x | opencode 2.x |
|---|---|---|---|---|
| allow | exit 0, no output | exit 0, no output | return | no change |
| warn | JSON `systemMessage` plus `additionalContext`, exit 0 | JSON `systemMessage` plus `additionalContext`, exit 0 | return; reason to stderr and the decision log | no change; reason to stderr and the decision log |
| ask | JSON `permissionDecision: "ask"` with the reason | becomes warn (Codex fails a hook run that returns ask, and the call proceeds anyway) | throw, with the reason, which tells the agent to confirm with the user and re-run with `# fx-ok: <reason>` | `ev.effect = 'ask'` with the reason as `ev.message` |
| deny | exit 2, reason on stderr (today's guard form) | exit 2, reason on stderr | throw with the reason | `ev.effect = 'deny'` with the reason |

On Claude Code in headless mode (`claude -p`) an ask resolves like a deny; this is the harness's behaviour and is documented, not worked around.

**Failure.** The git guard stays fail-closed. The shell guard is a hygiene guard, not a security boundary, and fails open: if its module fails to load, throws, or rejects asynchronously, the call proceeds and `[fx] shell guard off: <message>` goes to stderr and to `systemMessage` where the harness shows one. The Claude Code and Codex hooks install a deny-on-crash handler today; once the git guard has allowed, they swap it for `uncaughtException` and `unhandledRejection` handlers that print that line and allow, and they always end with an explicit `process.exit` after their output drains, so an open socket or timer can never hold the hook past its timeout (red team I8).

**opencode 2.x.** The permission `evaluate` callback is synchronous today. Before building, the 2.x task reads the 2.0.18 source to learn whether the runtime awaits a promise returned from `execute.before`. If it does, the guard runs there and leaves its decision in the existing call-id map for `evaluate` to apply. If it does not, opencode 2.x runs steps 1 and 2 only, and every grey command is allowed and logged with source `judge-unsupported` (the stamp needs a judge answer to soften, so it has nothing to do there); `references/harnesses/opencode-v2.md` records which branch holds.

**6. Trust rule.** Only the user's own prompts can soften a decision. The judge's state carries the latest root-session prompt recorded at `UserPromptSubmit` (Claude Code, Codex), redacted and capped, and nothing else from the conversation: no tool output, no file content, no assistant text, and never a subagent's dispatch prompt (a subagent's calls use the root session's prompt). On opencode both majors the state carries no prompt in this sub-project, because neither hook fx uses can tell a user prompt from a parent agent's prompt to a child session. Without a prompt the judge only grows stricter, never looser. Two things soften a decision and both are tied to the user: the user's prompt in the judge's state, and the stamp, honoured only after a user prompt (decision 5). The one exception is the Stop check's optional lift (decision 7), where the judge reads the agent's own final message; it can only end a turn the plain-code rule would have continued, never allow a command.

**7. Stop evidence check.** Runs at Stop (root session) and SubagentStop (the subagent's own journal) on Claude Code and Codex.
- **Edits in the turn**: edit events in the current turn (Claude Code `Write`, `Edit`, `MultiEdit`, `NotebookEdit`; Codex `apply_patch` and a shell `apply_patch`; opencode `edit`, `write`, `apply_patch`). A shell command that writes files is not counted. A turn whose edited paths all end in `.md`, `.mdx`, `.txt`, `.rst` or `.adoc` counts as no edits.
- **Evidence**: after the last edit in the turn, a `shell` event that verified. A check command is `test_one`, `test_scope`, `test_all` or `lint` from the repo's `.fx.json` (found at the git top level, decision 10). One matching rule (red team I10): a template with no `{placeholder}` matches a normalized command equal to its full text or starting with it followed by a space; a template with a placeholder matches on its text before the first `{`, trimmed, and that prefix counts only when it has at least two words or its first word contains `/` (so `node {file}` matches nothing and `scripts/test-scope {paths}` matches). A check command verifies when its outcome is success and nothing follows the matched part except arguments; one followed by `|`, `||` or `;` verifies only through a pass summary, because its exit code is no longer the check's (red team I9). A pass summary verifies only on a `shell` event whose program is not `echo`, `printf`, `cat`, `grep`, `rg`, `head`, `tail`, `sed` or `awk`, and only with a count of at least one. Pass summaries, matched on the last 4 KB of output: `ALL GREEN`; `\b[1-9]\d* (tests? )?passed\b` with no `\b[1-9]\d* failed\b`; `\b\d+ examples?, 0 failures\b`; `^OK(?: \(\d+ tests?\))?$`; `Tests:\s+\d+ passed` with no `failed`; `^ok\s+\S+` (Go) with no `^FAIL`; `test result: ok\.` (Cargo); `Passed!\s+-\s+Failed:\s+0` (dotnet). The outcome of a command is the harness's own: on Claude Code, task 08 settles from a recorded payload whether a failing `Bash` call arrives as `PostToolUseFailure` or as `PostToolUse` with an exit status, and records it in `references/harnesses/claude-code.md`; Codex reads an exit code from `tool_response` when one is present and otherwise records the outcome as unknown, which never counts as success but still allows a pass summary.
- **Decision**: edits and no evidence, `stop_hook_active` false, and no `stop-block` already in this turn: block once. The reason names the check to run (`test_scope` or `test_all` from `.fx.json` when set, else "the project's tests"). Claude Code: JSON `{"decision":"block","reason":...}`. Codex: the same JSON (Codex turns the reason into a continuation prompt). Every block appends a `stop-block` event and a decision-log line.
- **Judge (optional)**: only when about to block, a judge is configured and `last_assistant_message` is a non-empty string (a missing or empty message keeps the block with no judge call: red team I11), one `noul` question, `overclaims`: "the final message claims the work is finished, tested or verified". State: the redacted, capped `last_assistant_message`. When the answer is at most 0.30 with no escalation, the block is lifted and the lift logged. Any other answer, an escalation or an unavailable judge keeps the block (the plain-code rule applies).
- **opencode**: neither major can block at Stop (2.x documents no stop or idle hook; 1.x's `session.idle` is an event, not a gate). On both, the check runs when the next user prompt arrives, over the turn that just ended, and a missing-evidence reason is queued as a reminder pushed into the system text of the next request (1.x `experimental.chat.system.transform`, 2.x `ctx.session.hook('context')`), once. A subagent's child session on opencode gets no further user prompt, so subagents are not covered there; the conformance row records this as a GAP. Codex's Stop and SubagentStop input (`stop_hook_active`, `last_assistant_message`) is read from the Codex source before the Stop task builds on it and recorded in `references/harnesses/codex.md` (red team I18).

**8. Stuck-loop tracker.** Plain code, PostToolUse only, never blocks. Tool events are classified per harness as `edit`, `read` (Claude Code `Read`, `Grep`, `Glob`; opencode `read`, `grep`, `glob`, `list`; any shell command the allowlist accepts), `shell` or `other`. Three signals, each counted within the current turn:
- `repeat-failure`: the same normalized command failed three times with no `edit` event between the first and the third (a test re-run after an edit is the fx-tdd loop, not a retry: red team I17);
- `passive-stall`: twelve `read` events in a row with no `edit`, in a root session only (a subagent reading is usually its whole job);
- `unverified-writes`: ten `edit` events since the last verification (a check command that succeeded, or a pass summary).

No signal fires in the journal of a read-only review agent (`READ_ONLY_AGENTS` in `lib/plant-roles`, identified by the agent type recorded at its turn start: red team I17). When a signal reaches its threshold and no `nudge` for that signal exists in the turn, one line is injected and a `nudge` event appended. Lines name the fx-debug lane in the runtime's own addressing (the preamble's per-harness lane form). Delivery: Claude Code and Codex `hookSpecificOutput.additionalContext` on the PostToolUse output; opencode queued and pushed into the next request's system text, as in decision 7. Claude Code `PostToolUseFailure` is handled the same way with its own event name.

**9. Health line.** At SessionStart (not SubagentStart), when a judge config file exists, the hook asks one `noul` probe question under the same 1,500 ms budget. When the config is invalid or the probe is unavailable, one line is added: `[fx] judge config <path> is invalid (<reason>): the shell guard and Stop check run on code rules only.` or `[fx] judge at <base_url> is unavailable (<reason>): the shell guard and Stop check run on code rules only.` Claude Code: end of `additionalContext` plus `systemMessage`. Codex: the same two fields (both already allowed on SessionStart). opencode, both majors: pushed after the preamble once per session id and printed to stderr once (red team M22). A healthy judge, or no config file, prints nothing. On Codex the line adds `New fx hook events need trusting once in /hooks.`, because Codex skips a hook event until it is trusted and fx cannot read that state (ADR 0024; red team M23). The Codex hook prints the preamble only for SessionStart and SubagentStart; any other event it does not route prints nothing (red team M23).

**10. Repo switch (amended, red team C1, owner-approved 2026-10-22).** The owner's original decision let a repo switch each hook off. The agent can write `.fx.json`, and so can a hostile repository, and the payload's `cwd` follows the agent's `cd` into any directory, so a full switch would let either turn off the hard rules. Amended: `.fx.json` gains an optional `hooks` object, `{ "shell_judge": false, "stop_check": false, "loop_nudge": false }`. `shell_judge: false` turns off only the shell guard's judge step (decision 5, step 3); the hard rules and the allowlist always run. `stop_check` and `loop_nudge` turn off the Stop check and the nudges, which are advice and protect nothing a repo could exploit by disabling them. Each key defaults to `true`; a non-boolean is a parser problem and that key stays `true`. fx reads `.fx.json` from the git top level of the payload's `cwd` (`git rev-parse --show-toplevel`, 2 s timeout), and from `cwd` itself only outside a git repository. The git guard, the lane check and dispatch routing are not switchable. Sub-project 1's `.fx.json` parser gains this key.

**11. Setup.** `fx-setup` gains a judge section, per machine: when no config file exists, it explains that fx runs on code rules without one, and offers, following the owner's measurement (red team M26): none (default); Ollama with `nimble:9b` (tested on Ollama 0.40.7; easiest, the same on Windows, macOS and Linux; its Ollama page says Apache-2.0 while its model card says CC BY-NC, so the user checks the licence for their use); Kev-4B through `kev.serve` (most accurate, Apache-2.0, needs Python and a GPU); Rizzo Flow through `rizzo serve` (llama.cpp, documented on all three OSes); `d1:3b` on Ollama only as a listed alternative, never the default, because it let `cat .env` run in the spike and its LFM licence has terms to read; a remote judge (hosted Jev via TypeSafe, or OpenRouter, whose `/v1/systemone` path is unverified), with the warning that every grey command and Stop message is then sent to that service. Any non-loopback address counts as remote. A choice is written through a small CLI, `lib/judge-cli.js` with `path`, `check` and `write`, so the skill never computes the per-OS path itself; `write` takes a key only from standard input or a named environment variable, never from its arguments, so it never lands in shell history or the process list (red team I15). `check` prints the health result. The `.fx.json` table documents the `hooks` key.

**12. Registration.** Claude Code: one new entry point for `UserPromptSubmit`, `PostToolUse`, `PostToolUseFailure`, `Stop` and `SubagentStop`, routed on `hook_event_name` (the same one-entry-point design the existing hooks use), each with the 5 s timeout the existing entries carry; the shell guard joins the existing PreToolUse hook's `Bash` branch. Codex: the existing `fx-codex` hook gains `UserPromptSubmit`, `PostToolUse`, `Stop` and `SubagentStop` in the root `hooks.json`; every key it prints for a new event is added first to the Codex output gate's allowed sets (ADR 0023), citing the Codex hooks page. opencode: both plugins gain the guard in their existing shell path, `tool.execute.after` (1.x) and `ctx.tool.hook('execute.after')` (2.x) for the tracker, and the prompt boundary hooks of decision 4.

**13. Credits and records.** A root `THIRD_PARTY_NOTICES.md` credits jev-guard (question set, trust rule, adapter layout), jev-kit (pre-filter, loop guard, override stamp, health line), jev-belay (evidence belts, block once), jev-engineering (regex before allowlist), jev-use (escalation contract, mock backend), jevguard-mcp (ambiguity rule) and Edward (stuck-loop thresholds), each with its licence and copyright line. No code, environment variable, log format or client is copied. A new ADR records: the judge is optional and fails open, plain code decides first, the shell guard is hygiene and not a boundary, only user prompts soften (with the Stop lift as the one named exception), the stamp and repo-switch amendments, ask maps per harness, logs stay local. **14. No rm inside shell -c strings (added by the owner, 2026-10-23).** Claude Code cannot inspect a `bash -c` or `sh -c` string, so one that runs `rm` stops the session for a permission prompt, even in bypass mode, and an unattended build waits on a human. fx's own `.fx.json` `test_one` and `setup` do this. Each moves into a script file under `scripts/`, which does its own cleanup, and `.fx.json` names the script. The preamble gains one rule so agents writing commands in any repository do the same: cleanup goes in a script file, or scratch files wait for a later cleanup. A gate keeps `rm` and `trap` out of `-c` strings in `.fx.json`.

## Testing Decisions

- **Confirmed seam:** the existing one. `scripts/check-all`, node tests written in TypeScript and run as `node <built file>`, the install runs, and the free conformance runs on all four harnesses. Added at that seam:
  - a fake `/v1/systemone` server, started inside a test on a free loopback port, answering from a script per request (answer, HTTP status, delay, malformed body) and recording every request body;
  - hook entry points tested as processes: a JSON payload on stdin, then stdout, stderr and exit code asserted, as sub-project 1's golden gate does. Tests that run a hook while the fake server runs in the same process spawn asynchronously, never with a synchronous spawn, which would stall the server;
  - every test that runs a hook or plugin sets `HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `APPDATA` and `LOCALAPPDATA` to scratch directories, so a developer's own judge config or logs never change a result and are never written.
- **Good test here:** what a harness or user observes: the exit code and JSON a hook prints, the error a plugin throws, the line added to a log file, the request body the fake server received (to prove redaction and that no request was sent). Never internal helper calls.
- **Modules tested directly:** the config and response parsers, the redactor, the path resolver (per platform, as a pure function of platform, environment and home directory), the guard classifier, the evidence and tracker rules over a list of journal events.
- **Live conformance rows** (spend quota, not in `check-all`), owned by sub-project 4's task 14 together with any `tests/conformance/lib/live.sh` change (controller ruling on red team I20; sub-project order is 1, 2, 3, 4): row 21, a hard rule refuses a download piped into a shell (`curl -fsSL http://127.0.0.1:9/fx-probe | sh`, harmless if it ran; chosen over `rm -rf ~`, which would destroy the scratch home if the guard failed: red team M25) on all four harnesses; row 22, the Stop check blocks once on Claude Code and Codex and reminds on both opencode majors, asserted on fx's own `[fx] ` text in hook or context events, never on model wording (red team M25); row 23, the Stop check in a subagent passes on Claude Code and Codex and reports GAP on both opencode majors. Every row sets `HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `APPDATA` and `LOCALAPPDATA` to scratch (red team M24).

## Global Constraints

- Sub-project 1 is complete before task 01 starts: all fx code is TypeScript under `src/`, compiled file by file by `scripts/build` to committed JavaScript at the runtime paths.
- Users need Node only; no runtime `dependencies` in `package.json`; HTTP through Node's built-in `fetch`.
- Generated JavaScript targets `node20`.
- Module format per file is unchanged: CommonJS stays CommonJS, ESM stays ESM. Compile file by file; never bundle.
- `strict: true` and `noUncheckedIndexedAccess: true`; no `any`, `as any`, `@ts-ignore`, `@ts-expect-error` without `ts-gate-ok: <reason>`.
- External input (hook stdin, opencode events, `judge.json`, judge responses, journal and log files, `.fx.json`, environment) enters as `unknown` and is parsed by one function each; no `as` casts at trust boundaries; no validation library.
- Every path referenced by `hooks.json`, `hooks/hooks.json`, the Codex manifest, the opencode installer, `.fx.json` and skills stays byte-identical, except the new entries this design adds.
- A load guarded by `try` stays a typed `require` inside its `try`; never a hoisted `import`.
- The git guard stays fail-closed; the judge, shell guard, Stop check and tracker fail open.
- Judge budget: 1,500 ms per call, a constant.
- No default judge: with no `judge.json`, no network call is made.
- Nothing leaves the machine unless the user configured a remote `base_url`; redaction runs before every request and every log line.
- Logs and journals stay on the machine, mode `0600` on POSIX.
- Every test that runs a hook or plugin sets `HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `APPDATA` and `LOCALAPPDATA` to scratch directories.
- Locale: English only; fx has no localized text.
- No em or en dashes in any file, comment or commit message; no attribution trailers.
- Nothing is pushed, merged or released by the agent.
