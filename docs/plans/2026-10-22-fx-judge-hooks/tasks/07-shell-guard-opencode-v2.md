# 07: Shell guard on opencode 2.x

**Status:** ready-for-agent
**Blocked by:** 06
**Phase:** Core

**What to build:** the opencode 2.x plugin runs the shell guard on every `shell` call, after the git guard, using opencode's own permission effects: deny sets `deny`, ask sets `ask` (2.x has a real ask), each with the reason as the message. Hard rules and the read-only allowlist always run, in the synchronous `permission.evaluate` hook. Whether the judge can run depends on one fact read from the 2.0.18 source first: whether the runtime awaits a promise returned from a `tool.execute.before` callback. If it does, the judge runs there and leaves its decision for `evaluate` to apply. If it does not, 2.x runs code rules only and logs each grey command as `judge-unsupported`; `references/harnesses/opencode-v2.md` says which holds. A new user prompt marks a turn boundary through `ctx.session.hook('prompt')`; if that hook cannot be registered, fx says so on stderr only (never in the session's misinstalled list) and the harness reference records the gap. A dead judge is reported once per session in the context text and once on stderr.

**Interfaces:**
- Consumes: `guardShell`, `classifyShell`, `overrideReason`, `normalizeCommand` (task 03); `judgeHealth` (task 04); `journalKey`, `appendEvent` (task 02); the plugin's existing `commands` map and `callKey` (sub-project 1 port of today's code); test helpers (task 01).
- Produces: `guardShellCodeOnly(input: { command: string, cwd: string, harness: Harness, sessionId: string | null }) -> GuardDecision` (synchronous: hard rule gives deny, `hard-rule`; read-only or repo command gives allow, `read-only` or `repo-command`; else allow, `judge-unsupported`; logs as `guardShell` does; it never asks a judge, never honours a stamp, which needs a judge answer to soften, and never applies the loop guard).
- Produces, branch A (the runtime awaits `execute.before`): `execute.before` for `shell` records the command as today, then awaits `guardShell({ ..., harness: 'opencode-v2', sessionId: ev.sessionID, agentId: null })` (so a loop-guard repeat and an honoured stamp both give ask) and stores the decision in a second map under the same `callKey`; `evaluate` for `shell`, after the git guard allows, reads that decision: deny sets `ev.effect = 'deny'` and `ev.message = reason`; ask sets `ev.effect = 'ask'` and `ev.message = reason`; warn and allow change nothing (warn's reason goes to stderr). A missing decision falls back to `guardShellCodeOnly`. `execute.after` deletes both entries.
- Produces, branch B (not awaited): `evaluate` for `shell`, after the git guard allows, applies `guardShellCodeOnly` on the recorded command (deny as above; allow changes nothing).
- Produces: `ctx.session.hook('prompt', ...)` appends `{ kind: 'prompt', text: null }` to `journalKey(<session id from the payload>)`; when the payload carries no session id, it does nothing. It is registered outside the plugin's `attempt()` failure list (red team I19): a registration failure prints `[fx] the prompt hook is unavailable: <message>; the Stop reminder and stamp cannot work on this opencode.` to stderr only, and `references/harnesses/opencode-v2.md` records the GAP.
- Produces: health computed once at `setup` without awaiting it, printed to stderr once when non-null; the `context` hook pushes the line once per session id after it has settled to a non-null value (a request that arrives before it settles pushes nothing and the next one tries again).

**Seam:** the plugin's `setup` called in-process with a fake `ctx`, as `tests/gates/opencode-v2-plugin.test.js` does today.
