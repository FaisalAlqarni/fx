# 02: Catalog writer, profile ownership and CLI

**Status:** ready-for-agent
**Blocked by:** 01
**Phase:** MVP

**What to build:** `setupCatalog`, which reads the user's Codex `config.toml` (never writes it), asks Codex for its model entries, calls `buildCatalog`, and writes two files into `$CODEX_HOME`: the catalog `fx-<provider>.catalog.json` and the profile `fx-<provider>.config.toml` holding one key, `model_catalog_json`, plus fx's marker. It writes only files that are absent or carry fx's marker, and reports everything. A thin CLI, `node lib/codex-catalog.js setup [slug...]`, prints the report as JSON. fx-setup (task 04) and the conformance runner (task 05) both call this path.

**Design:** Implementation Decisions; User Stories; Testing Decisions; Global Constraints

**Files:**
- Modify: `src/lib/codex-catalog.ts` and its build output `lib/codex-catalog.js`
- Modify: `src/lib/codex-catalog.test.ts` and `lib/codex-catalog.test.js`

**Interfaces:**
- Consumes: `buildCatalog`, `loadFallback`, `CATALOG_MARKER` (task 01).
- Produces:
  ```ts
  export const PROFILE_MARKER: string   // first line of the profile file
  export interface SetupReport {
    provider: string | null;             // model_provider from config.toml, null when unset
    slugs: string[];                     // slugs asked for, config model first
    profile: string | null;              // 'fx-<provider>' when written or current, else null
    command: string | null;              // 'codex --profile fx-<provider>' when profile is set, else null
    written: string[];                   // absolute paths written this run
    kept: string[];                      // same-named files fx did not write: left alone
    cloned: string[];
    refused: { slug: string; reason: string }[];
    skipped: string | null;              // why nothing was attempted, else null
  }
  export function setupCatalog(args?: { codexHome?: string; slugs?: string[]; listModels?: () => unknown[] }): SetupReport
  ```
  `PROFILE_MARKER` is exactly `# generated by fx (lib/codex-catalog.js): fx-setup rewrites this file; edit your own config.toml instead`.
- CLI: `node lib/codex-catalog.js setup [slug...]`. Prints `JSON.stringify(report)` on stdout. Exit 0 when `profile` is non-null; exit 3 when nothing was written (skipped, everything refused, or a file kept); exit 1 on an error, with the message on stderr and nothing on stdout. Any other first argument prints a usage line to stderr and exits 2.

**Behaviour, exactly:**
- `codexHome` defaults the way `plantRoles` resolves it in `src/lib/plant-roles.ts`: `parseFxEnv(process.env).codexHome`, else `~/.codex`.
- From `<codexHome>/config.toml` read only the top-level string keys `model` and `model_provider`: lines before the first line that starts with `[`, of the form `key = "value"`. A missing file reads as both unset. The file is never written, renamed or touched.
- Slugs: the config `model` when `model_provider` is set and is not `openai`, then each named slug, de-duplicated, in that order. With no slugs, return `skipped: 'no third-party model in config.toml and no slug named'` without calling `listModels`.
- The provider name for the file names is `model_provider`; when it is unset or `openai` and slugs were named, use `custom`. A provider name that does not match `/^[A-Za-z0-9_-]+$/` throws `Error('provider name not usable in a file name: <name>')`.
- `listModels` defaults to running `codex debug models` with `child_process.execFileSync('codex', ['debug', 'models'], { encoding: 'utf8', maxBuffer: 256 * 1024 * 1024 })` and returning the parsed `models` array. It never passes `--profile`, so a re-run reads Codex's own view, not fx's earlier catalog. A non-zero exit or unparseable output throws.
- Ownership. The profile file is fx's when it is a regular file (not a symlink) whose first line equals `PROFILE_MARKER`. The catalog file is fx's when it is a regular file whose JSON has `fx_generated === CATALOG_MARKER`. An absent file may be written. If either existing file is not fx's, write neither, list it in `kept`, and return `profile: null`.
- When `buildCatalog` returns no models (all refused), write nothing.
- Otherwise write the catalog as `JSON.stringify(catalog, null, 1) + '\n'`, then the profile as exactly two lines: `PROFILE_MARKER`, then `model_catalog_json = <JSON.stringify(absolute catalog path)>`, each followed by `\n`. Both files mode 0600. Both paths go in `written` (also when the content was identical; a re-run reports what it rewrote).

**Seam:** `setupCatalog` with an injected `listModels` and a temp `codexHome`; the CLI through `child_process.spawnSync(process.execPath, ['lib/codex-catalog.js', 'setup'])` with a stub `codex` first on `PATH`.

- OpenRouter model: `config.toml` is `model = "anthropic/claude-haiku-4.5"\nmodel_provider = "openrouter"\n\n[model_providers.openrouter]\nname = "openrouter"\n`; `listModels` returns one Haiku entry (task 01 shape). The report has `provider === 'openrouter'`, `slugs` deep-equals `['anthropic/claude-haiku-4.5']`, `profile === 'fx-openrouter'`, `command === 'codex --profile fx-openrouter'`, `written` deep-equals `[<home>/fx-openrouter.catalog.json, <home>/fx-openrouter.config.toml]`. The profile file's text equals `PROFILE_MARKER + '\nmodel_catalog_json = ' + JSON.stringify(<home>/fx-openrouter.catalog.json) + '\n'`. The catalog's `models[0].include_skills_usage_instructions === true`. `config.toml`'s bytes are unchanged.
- A user's same-named profile is kept: before the run, `fx-openrouter.config.toml` holds `model = "x"\n`. Report: `profile === null`, `kept` deep-equals `[<home>/fx-openrouter.config.toml]`, `written` is `[]`; the file still holds `model = "x"\n`; no catalog file exists.
- A symlinked profile is kept: `fx-openrouter.config.toml` is a symlink to a file carrying the marker. Same result as above; the link target is unchanged.
- Re-run after a model change rewrites: run once with the Haiku config, then change `config.toml`'s model to `openai/gpt-6.1-sol` and run again with `listModels` returning a GPT entry with no `# Skills` text. The catalog's `models.map(m => m.slug)` deep-equals `['openai/gpt-6.1-sol']`.
- No third-party model: `config.toml` holds `model = "gpt-6.1-sol"\n` and no provider. Report `skipped === 'no third-party model in config.toml and no slug named'`, `written` is `[]`, and `listModels` was never called.
- Named slugs: OpenRouter Haiku config and `slugs: ['openai/gpt-6.1-sol', 'anthropic/claude-haiku-4.5']`. Report `slugs` deep-equals `['anthropic/claude-haiku-4.5', 'openai/gpt-6.1-sol']`.
- Everything refused: `listModels` returns the Haiku slug with `include_skills_usage_instructions: true`. Report `profile === null`, `written` is `[]`, `refused.length === 1`, and no file named `fx-openrouter.*` exists.
- Bad provider name: `model_provider = "open router"` throws with message `provider name not usable in a file name: open router`.
- CLI: a temp dir `bin/` holds an executable stub `codex` (a `#!/bin/sh` file whose body prints a fixed models JSON when its arguments are `debug models`, and exits 1 otherwise); env `PATH=<bin>:<original PATH>`, `CODEX_HOME=<temp home>` holding the OpenRouter config. Exit status `0`; stdout parses and `profile === 'fx-openrouter'`; both files exist. A second CLI run against a `CODEX_HOME` with no `config.toml` exits `3` and prints `skipped`. `node lib/codex-catalog.js nope` exits `2`.

Expected: exit 0 and exactly one model, `anthropic/claude-haiku-4.5`, with `include_skills_usage_instructions` true and `apply_patch_tool_type` `freeform`. If Codex refuses the `fx_generated` key, move the marker into the profile file only (the catalog is then fx's when the fx profile file names it) and update the Interfaces and tests to match; say so in the report.

**Risks:** never call `codex` with `--profile` from `setupCatalog`, or a re-run reads its own previous catalog (one model) instead of the provider's list.

**Idempotency:** a re-run rewrites only fx-marked files with fresh content and leaves every other file alone; running it twice in a row gives the same files.

**Testing:** unit plus a CLI integration test in `node lib/codex-catalog.test.js`; the live check above.
