# Codex integration: how superpowers does it, where fx departed, and the root cause of Codex + Haiku skipping lanes

Date: 2026-10-28. Question: on Codex CLI 0.164.0 with `anthropic/claude-haiku-4.5` over OpenRouter, the model skips fx's lanes and writes code with no design (diagnosis: `/tmp/claude-1000/fx-codex/findings.md`). How does upstream superpowers make Codex use its skills, why does fx have the problem, and what is the real fix?

Sources, all primary:

- superpowers: `git clone https://github.com/obra/superpowers` into `/tmp/claude-1000/sp-research/superpowers`, tag `v7.0.1` and history (cited as `SP:<path>:<line>` at v7.0.1 unless a commit or tag is named). Issues and PRs through the public GitHub REST API (`gh` is not installed).
- Codex: `openai/codex` tag `rust-v0.164.0` (commit `6aaac69`), cloned into `/tmp/claude-1000/sp-research/codex` (cited as `CX:<path>:<line>`, paths under `codex-rs/`). Docs: https://learn.chatgpt.com/docs/build-skills and https://learn.chatgpt.com/docs/hooks (the `developers.openai.com/codex/*` URLs 308-redirect there).
- fx: `/development/fx` at `ce1fb19` (v0.7.0).
- The runs: `/tmp/claude-1000/fx-codex/runs/*` rollouts.

`/mnt/d/Projects/superpowers` was not used: git refuses it (dubious ownership) and the clone above is the upstream.

## Answer

1. **superpowers on Codex ships no bootstrap at all.** Since v6.1.0 (2026-06-30) its Codex manifest declares `"hooks": {}` and nothing else carries the 1% rule. It relies entirely on Codex's own skill machinery: the skill catalog, plus the "you must use that skill" trigger rules that Codex itself adds. superpowers removed its Codex SessionStart hook because "Codex reliably triggers skills on its own, and the SessionStart hook made the UX worse rather than better" (commit `640ce6c`).
2. **Codex adds those trigger rules only for models it knows.** For a model slug missing from the bundled catalog (every OpenRouter slug), Codex uses fallback metadata with `include_skills_usage_instructions: false` and `apply_patch_tool_type: None`, and a base prompt that never mentions skills. So a Codex + OpenRouter model gets a bare list of skills with no rule to use them, and no edit tool. The Haiku rollouts contain no `How to use skills` section (0 matches in all three checked).
3. **fx departed by porting its Claude Code shape to Codex**: an always-on preamble from SessionStart, and a lane check on the edit tool. Two primitives hold that shape up on Claude Code: a `Skill` tool the harness tells the model to call first, and an edit tool every write goes through. On Codex with a non-catalog model, neither exists. ADR 0020 decided that only the *names* differ per runtime. That premise holds on Claude Code and opencode, and fails on Codex.
4. **superpowers has the same weakness, worse, and has never addressed it.** On Codex + Haiku over OpenRouter, superpowers would give the model nothing but skill descriptions. Its Codex evals run on OpenAI-account models only. The real fix is to give Codex the two missing primitives through Codex's own supported mechanism, the model catalog. It is not to re-send the preamble or to parse heredocs. Section 5 has the details.

### State at v7.0.1

- **Bootstrap delivery on Codex:** none. `"hooks": {}` (`SP:.codex-plugin/plugin.json:24`). `docs/porting-to-a-new-harness.md:240-243`: Codex "surfaces skills natively and runs no session-start hook."
- **Skill discovery:** Codex's native catalog, from the plugin manifest's `"skills": "./skills/"` (`SP:.codex-plugin/plugin.json:23`).
- **How the 1% rule reaches the model:** only by the model choosing the `using-superpowers` skill from the catalog. Its description is "Use when starting any conversation - establishes how to find and use skills, requiring skill invocation before ANY response including clarifying questions" (`SP:skills/using-superpowers/SKILL.md:3`). The brainstorm gate is the brainstorming description: "You MUST use this before any creative work - creating features, building components, adding functionality, modifying behavior..." (`SP:skills/brainstorming/SKILL.md:3`).
- **How a skill is invoked:** the model reads `SKILL.md` through its shell, as Codex's own catalog instructions say. using-superpowers says "Invoke relevant or requested skills BEFORE any response or action, including clarifying questions, exploring the codebase, or checking files" (`SP:skills/using-superpowers/SKILL.md:20`). On Codex, invoking is the first read, so the rule does not contradict itself there.
- **Tool mapping:** `SP:skills/using-superpowers/references/codex-tools.md` covers only multi-agent (`spawn_agent`, `wait_agent`, `followup_task`), model routing, worktree detection and Codex App finishing. The `TodoWrite` to `update_plan` mapping was pruned in v6.1.0 as guidance "modern agents already follow" (`SP:RELEASE-NOTES.md:248`).
- **What stops coding before brainstorming:** only skill text (the descriptions and the brainstorming hard gate). No hook and no enforcement on Codex. Issue #2372 (open, 2026-09-23) shows that this fails even on gpt-6-sol: Codex Desktop "read `using-superpowers` and `brainstorming`; hard gate text returned", then installed the SDK, scaffolded and committed code with no approval. Its own explanation was that "it interpreted the initial build request as permission to start". Issue #2506 (open) reports a similar skip of worktree consent on Codex.
- **Which models superpowers measures on Codex:** OpenAI-account models. `first-turn.sh` (commit `8983a20`) runs Codex in a throwaway `CODEX_HOME` "holding only a symlink to `~/.codex/auth.json`", with `-m` such as `gpt-6-luna`. `codex-with-plugin.sh` keeps the account's curated plugin. No Codex run with a non-OpenAI provider was found in the tree, the branches or the issues searched.

## 2. Codex's own mechanism, at rust-v0.164.0

### How skills reach the model

- The catalog is a developer fragment wrapped in `<skills_instructions>`: "## Skills", an intro, a `### Skill roots` alias table, then `### Available skills` (`CX:ext/skills/src/catalog_prompt.rs:84-112`). For plugin (host) skills, the intro says each entry has "a short path that can be expanded into an absolute path using the skill roots table" (`:4`).
- **The trigger rules are optional.** `AvailableSkillsInstructions::from_skill_lines` appends `### How to use skills` and the usage block only when `include_skills_usage_instructions` is true (`CX:ext/skills/src/fragments.rs:21-33`). The flag comes from the model's `ModelInfo` (`CX:ext/skills/src/extension.rs:222-224`). The usage block for host skills reads: "Trigger rules: If the user names a skill ... OR the task clearly matches a skill's description shown above, you must use that skill for that turn", and "the main agent must expand the listed short `path` with the matching alias from `### Skill roots`, then open and read its `SKILL.md` completely before taking task actions" (`CX:ext/skills/src/catalog_prompt.rs:24-28`).
- **Bundled models:** `models-manager/models.json` sets `include_skills_usage_instructions` true only for `gpt-5.5`. The current GPT entries (`gpt-6.1-sol` at line 177, and others) carry false, because their own `model_messages.instructions_template` has a `# Skills` section instead. That section says "Do not use a skill based solely on keywords, superficial relevance, or the availability of a potentially applicable skill" and "If a skill does not explicitly require approval, default to proceeding within the user's authorized scope" (`models.json` lines 76, 250, 424). Those GPT models also get `apply_patch_tool_type: freeform`.
- **Unknown models (every OpenRouter slug):** `construct_model_info` falls back to `model_info_from_slug` when no catalog entry matches (`CX:models-manager/src/manager.rs:942-956`). The fallback sets `include_skills_usage_instructions: false` (`CX:models-manager/src/model_info.rs:117`), `apply_patch_tool_type: None` (`:124`), and base instructions `BASE_INSTRUCTIONS = include_str!("../prompt.md")` (`:16`, `:151-155`). `prompt.md` (20,903 bytes) never mentions skills. It does carry the AGENTS.md spec (`CX:models-manager/prompt.md:17-27`) and "keep going until the query is completely resolved ... Autonomously resolve the query" (`:125`). The apply_patch tool is registered only when `apply_patch_tool_type.is_some()` (`CX:core/src/tools/spec_plan.rs:1409`).
- **Verified in the runs:** `grep -c 'How to use skills'` gives 0 in the rollouts of `e2-codex-haiku-2`, `e3a-codex-sonnet55` and `v1-last-haiku-2`. On Codex + OpenRouter, Haiku, Sonnet and GPT alike see a skill list with no instruction to use it. fx's preamble is the only skill rule in their context.
- **Invocation:** explicit `$name` mentions inject the full `SKILL.md` as a `<skill>` user fragment (`CX:ext/skills/src/fragments.rs:73-105`). That is user syntax. Implicitly, the model reads the file with its shell, because host skills have no tool: `skills.read` serves only executor and cloud packages (`CX:ext/skills/src/tools/mod.rs:293-309`). Docs: "ChatGPT and Codex start with each skill's name and description"; "In Codex, the initial list also includes each skill's file path"; the list is capped at "2% of the model's context window"; `policy.allow_implicit_invocation: false` in `agents/openai.yaml` limits a skill to `$` mentions (https://learn.chatgpt.com/docs/build-skills).

### Other always-on channels

- **AGENTS.md:** `$CODEX_HOME/AGENTS.override.md` or `AGENTS.md` (`CX:codex-home/src/instructions/mod.rs:12-13, 43`), then every `AGENTS.md` from the project root to cwd (`CX:core/src/agents_md.rs:1-18`). These are user and repo files. A plugin cannot add one.
- **`developer_instructions`** ("inserted as a `developer` role message") and **`model_instructions_file`** (overrides the built-in instructions; "Users are STRONGLY DISCOURAGED from using this field") are user or project config (`CX:config/src/config_toml.rs:252-275`).
- **`model_catalog_json`:** "Optional path to a JSON model catalog (applied on startup only)" (`CX:config/src/config_toml.rs:406-408`). "When set, this replaces the bundled catalog for the current process" (`CX:core/src/config/mod.rs:1054-1056`). This is Codex's supported way to declare a model's `ModelInfo`, including `include_skills_usage_instructions`, `apply_patch_tool_type` and `model_messages`.
- **Hooks:** `SessionStart`, `SubagentStart` and `UserPromptSubmit` take `additionalContext` as "extra developer context". `PreToolUse` sees shell as `Bash` (including `exec_command`) and edits as `apply_patch`/`Edit`/`Write`. It can deny. The docs say: "Treat tool hooks as a useful guardrail, not a complete enforcement boundary." Plugin hooks need trust in `/hooks` (https://learn.chatgpt.com/docs/hooks).
- **Provider differences:** the code has no per-provider branch for skills. The difference is per model slug: a slug outside the catalog gets the fallback `ModelInfo` above. The findings show `openai/gpt-6.1-sol` over OpenRouter also misses the catalog and gets the generic prompt.

## 3. fx's Codex integration as it stands

- **Install:** `.codex-plugin/plugin.json` declares `"skills": "./skills/"` and `"hooks": "./hooks.json"` (lines 17-18; ADR 0022). Roles are planted into `$CODEX_HOME` at SessionStart (ADR 0024, ADR 0028).
- **Preamble:** `hooks.json` runs `hooks/fx-codex.js` on SessionStart (matcher `startup|resume|clear|compact|fork`) and SubagentStart, with `additionalContextLimit: 0`. It renders `PREAMBLE.md` for `codex` (`src/hooks/fx-codex.ts:598`). The Codex render (`src/lib/preamble.ts:67-77`) fills `PREAMBLE.md:14-17` as: invoke a lane "with your shell to read the lane's `SKILL.md` in full **before any response**, including before a clarifying question and before reading a single file". Lanes are addressed `$fx:fx-tdd`, and the model is told "The runtime lists each lane's `SKILL.md` path". UserPromptSubmit only journals the prompt (`fx-codex.ts:524-527`).
- **Skills surfacing:** Codex's native catalog only, the same as superpowers. Some user-invoked lanes ship `agents/openai.yaml` (ADR 0025).
- **Guards:** PreToolUse lane-checks paths from `apply_patch`, either the tool or `apply_patch` run in the shell (`fx-codex.ts:262`, `:329-330`, `:346-347`; ADR 0039). `lib/lane-check.ts:63-73` is advice that fires once: "about to write X, and this repo has no docs/plans/*/design.md". The session journal and the Stop check count edits from edit tools (ADR 0051), so a heredoc write is a `shell` event to them too.
- **Harness doc:** `references/harnesses/codex.md:12-13`: "Everything goes through the shell. Edits go through `apply_patch`." That second sentence is false for a non-catalog model, which has no apply_patch tool.

## 4. Where and why fx departed from superpowers

fx never decided "Codex gets a bootstrap, unlike superpowers". It carried the Claude Code bootstrap to every runtime and decided only how the names render.

- **ADR 0021** (2026-09-22) took superpowers as the model: "superpowers injects a 3.1KB bootstrap and leaves routing to each skill's own description, which every runtime already shows the model." On Codex that was already untrue. superpowers had stopped injecting anything on Codex in v6.1.0, twelve weeks earlier. The ADR's measurement covers "Claude Code: 9 of 9 lane prompts ... opencode on the local 27B model: 9 of 9". Codex was not measured.
- **ADR 0020** (2026-09-21): "Each injector renders it through one shared function before injecting, so every session sees a concrete, correct, self-sufficient imperative, with no indirection and no read." It also says: "A pointer inside the imperative ... asks the agent to perform a read before it can act, in the same paragraph that tells it **invoke, do not read**." On Codex, invoking *is* a read, so the rendered imperative ("read the lane's SKILL.md ... before reading a single file") contains the contradiction the ADR was written to prevent. The render changed the tool phrase and kept the Claude Code ordering clause.
- **ADR 0039** (2026-10-01) met the no-apply_patch case ("A model reached over chat completions has no `apply_patch` function tool") and widened the check by matching command text. That started the pattern the owner now rejects.
- **ADR 0002 / 0001:** order is force, and instruction comes before enforcement. Both hold. The failure here is not missing instruction. It is that the instruction asks for an action Codex does not frame as the first action, for a model to which Codex gives no skill contract.

The one design difference: **superpowers delegates "use skills first" to Codex and ships nothing. fx supplies it itself, in Claude Code's form, and assumes Codex supplies the rest: a skill-first contract and an observable edit tool.** For catalog GPT models Codex does supply both, so fx and superpowers both work there. For non-catalog models Codex supplies neither. superpowers then has nothing. fx has a late preamble whose ordering clause is wrong for Codex, plus a guard on a tool the model does not have.

## 5. Root cause and the real fix

### Root cause

On Codex, two things decide whether a model uses skills and whether a write is visible to a hook: the model's `ModelInfo`, namely `include_skills_usage_instructions` (or a base prompt with a skills section) and `apply_patch_tool_type`. For every OpenRouter slug, Codex uses fallback metadata that switches both off (`CX:models-manager/src/model_info.rs:98-124`). fx's Codex design assumes both are on. That assumption is ADR 0020's "only the names differ" plus `references/harnesses/codex.md:13`'s "Edits go through apply_patch". fx never checks it. Sonnet and GPT get by on the preamble alone. Haiku does not. The model makes the problem worse, but the cause is the missing contract.

superpowers has the same weakness, worse, since it ships no rule at all on Codex. It has never addressed it, because it tests only catalog models.

### The real fix: declare the model to Codex, then render for what Codex actually does

1. **Give Codex a catalog entry for the non-catalog model (`model_catalog_json`).** Codex already uses this mechanism to decide skill rules and edit tools. Clone the fallback `ModelInfo` for the configured slug and set `include_skills_usage_instructions: true`. Codex then adds its own "Trigger rules ... you must use that skill" and "expand the short path ... read SKILL.md completely before taking task actions" block, inside the same message as the skill list (`catalog_prompt.rs:24-28`). That is the slot superpowers relies on. Set `apply_patch_tool_type: "freeform"` if the provider accepts Responses `custom` tools (open question 1). Writes then go through `apply_patch`, and fx's existing lane check, edit rules, journal and Stop check see them without parsing any shell text. Because the catalog replaces the bundled one (`config/mod.rs:1054-1056`), put it in a Codex profile for that provider, not at top level.
   - Who writes it: fx-setup generates the file and reports the `config.toml` lines for the user to add. fx-setup does not edit `~/.codex/config.toml` itself (fx-setup's practice, restated in `compare-6-authoring-new.md:162`). The conformance runner (`src/tests/conformance/lib/openrouter.ts:60-85`) writes the same entry, so the live rows run the shape users get.
   - This replaces ADR 0039's `SHELL_APPLY_PATCH` text match as the main path, which then becomes a fallback for providers that cannot take the tool. It also replaces any plan to re-send the preamble every turn or to parse heredocs.
2. **Correct the Codex render, as ADR 0020 already requires ("concrete, correct, self-sufficient").** On Codex, invoking a lane is reading its file. So the imperative should say: read the lane's `SKILL.md` first, before any other file. Give the absolute path, which the hook knows at render time from the plugin root, instead of "the runtime lists each lane's path". Drop "before reading a single file", and keep `$fx:fx-tdd` as the name the user types, not as the action. This changes `src/lib/preamble.ts:67-77` and the `{{READ_RULE}}` slot only. Nothing goes above the imperative (ADR 0002 holds).
3. **Write down the fact in the harness layer (ADR 0016).** Correct `references/harnesses/codex.md:12-13`: a non-catalog model gets no skill trigger rules and no apply_patch unless a catalog entry declares them. Supersede the "names only" premise of ADR 0020 for Codex with a new ADR: "On Codex, fx declares the model; the runtime supplies the skill contract."

Kept as they are: the SessionStart and SubagentStart preamble. superpowers dropped its Codex hook, but on non-catalog models Codex gives no other skill rule, and SubagentStart is the only channel into children (`research/codex.md` section 4).

Not proposed: an AGENTS.md block. It is the v3.3.0 superpowers shape and lives in user files. The findings show Haiku reads AGENTS.md ("Let me check for AGENTS.md"), so it is worth one arm in the experiment, but it duplicates the preamble in a different slot.

### Evidence that would prove it (Codex 0.164.0 + `anthropic/claude-haiku-4.5`, OpenRouter, the Ledgerly seed and `prompts/baseline.txt` from `/tmp/claude-1000/fx-codex`)

Probe first, 1 run: catalog entry with `apply_patch_tool_type: "freeform"`. Does OpenRouter accept the request, and does Haiku call `apply_patch`? Then 10 runs per arm. The baseline is the existing 10 (`e2*`, `codex-r1/r2`, `v*` baselines). The cost is about USD 0.12 per run at the measured USD 1.39 for 12.

## Open questions

1. Does OpenRouter's Responses endpoint accept a Codex `custom` (freeform) tool and return `custom_tool_call` items for Anthropic models? llama-server does not (`codex-local-model.md:63`). This decides whether item 1 also fixes write visibility, or only the skill contract.
2. With `include_skills_usage_instructions: true`, does the bundled usage block conflict with fx's 1% rule the way the GPT prompt's "Do not use a skill based solely on keywords" does? The host-alias block has no such line (`catalog_prompt.rs:24-40`), but A1 should be read for it.
3. Does an OpenRouter provider with `auth.command` fetch `/models` and get a remote `ModelInfo` that overrides the local catalog? `codex-local-model.md:28` says only providers *without* command auth skip the fetch. This needs checking against 0.164 before relying on the catalog entry.
4. Should fx-setup write the catalog file, or only report it? This is the owner's call under the "fx-setup never edits Codex config" practice.
5. superpowers PR #2088 says `codex exec` on 0.146.0 ran no startup hook, while fx's runs on 0.164 show the hook firing under `--dangerously-bypass-hook-trust`. Confirm on 0.164 without the bypass flag (trusted through `/hooks`), since that is what users run.
