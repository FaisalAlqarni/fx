### Issues

**Critical**

1. `tests/review-bench/cases/search-case-sensitive/match:1` and `tests/review-bench/cases/search-query-only/match:1`: the regex is the single word `case`, case-insensitive. This is exactly the failure mode the review's own Focus section warns against ("a regex matching 'case' could match 'test case'"). Demonstrated directly: a findings file whose only Important line is `test/search.test.js:12 - this test case only checks the happy path, add a failing lookup case too` (no mention of case-folding at all) scores `{"caught":true,...}` against this match. Any Important finding that uses the ordinary English word "case" for any reason (test case, edge case, corner case, "in this case") is scored as catching the case-insensitivity defect whether or not it does. This invalidates the catch-rate measurement for 2 of the bench's 9 cases. Fix: tighten to something that names the behavior, e.g. `case[- ]?(insensitiv|fold|sensitiv)|toLowerCase|upper.?case|mixed.?case`, or require the word adjacent to "search"/"query"/"match".

**Important**

2. `tests/review-bench/rows/01-review-bench.sh:40-45`: the bench's diff shape is unrealistic. `BASE` is the bare fixture seed (`tests/fixture-build/repo/`: `.fx.json`, an empty `README.md`, `lib/.gitkeep`, `test/.gitkeep`, no implementation at all), and `HEAD_SHA` is that seed plus the case's full five-module `files/`. A reviewer told it is reviewing task 01 (say) sees `README.md`, `cli.js`, `lib/export.js`, `lib/search.js` and `lib/store.js` all created from nothing in one diff, none of which task 01 asked for except `lib/store.js`. A real per-task review only ever sees that task's own file(s) layered on the prior tasks' committed work. This both dilutes the planted defect among four unrelated new files and risks the reviewer spending its budget on "extra scope" findings (a real risk with this diff shape, since Part 1 of the template explicitly asks it to flag unrequested files) instead of the one defect the bench is trying to measure. Fix, per the task's own suggested shape: base = seed plus the good reference implementation of every file except the case's task's file(s); head = base with the case task's file(s) replaced by the case version. For example, `path-no-check` (task 01, `lib/store.js`) would have `README.md`, `cli.js`, `lib/export.js`, `lib/search.js` already committed at base (from the `good` reference), and the head commit would touch only `lib/store.js`.
3. `tests/review-bench/rows/01-review-bench.sh:32-38`: `GLOBAL_CONSTRAINTS` is extracted only from `plan.md`'s `## Global Constraints` heading (three process-level bullets), never from `docs/plans/2026-01-01-notes/design.md:38-44`'s "Storage and search rules" section, which states the exact rules six of the nine planted defects violate (`EBADNAME` containment, `ENOTE` vs. empty, case-insensitive search). Per Ruling K in `docs/plans/2026-09-23-lean-build/state.md`, those rules were deliberately moved out of task prose and into the design's body; per `task-reviewer-prompt.md`'s own placeholder definition, `[GLOBAL_CONSTRAINTS]` is meant to include binding requirements from "plan.md or design.md," not plan.md alone. This is plan-mandated (the 03b task file literally says "the fixture plan's Global Constraints verbatim"), but it means the bench reviewer, for 6 of 9 cases, gets no textual definition of the exact contract it is checking against and must catch the defect purely from general code-quality/security judgment rather than a stated requirement: a materially harder task than a real review, which per the template's own contract would have design.md's relevant rules copied in too. Worth the owner's attention before task 04 reads bench output as a quality gate: either fold the "Storage and search rules" section into `GLOBAL_CONSTRAINTS`, or explicitly accept that these cases measure judgment-based catching, not spec-based catching, and interpret results accordingly.

**Minor**

4. `tests/review-bench/score.js:45`: `bulletCount` assumes every finding is a single line starting with `- ` (`^\s*-\s+\S`). A reviewer that numbers findings, wraps a finding across two lines, or otherwise deviates from the ledger's own dash convention undercounts `important`/`falsePositive` silently (no exit 2, since the heading itself is still present). Already disclosed in the implementer's report as a known risk; not exercised since the live bench doesn't run in this task. Worth a follow-up note in the bench's own findings/logs when task 04 runs it, per the task's own risk item about auditing misses from kept logs.
5. `tests/review-bench/cases/readme-binary/match:1` (`binary|node cli\.js|not installed`): `node cli\.js` is a reasonably common phrase to appear in an unrelated finding about this fixture (any correct usage example in a finding elsewhere would use it), though less generic than issue 1's bare `case`. Lower risk, not demonstrated as a false catch, but worth tightening if the owner is already touching `match` files for issue 1 (e.g. anchor to "should be" or "instead of").

### Assessment

**Needs fixes.** The mechanics (`score.js`, `fill-template.js`, refusals, `run.sh`, wiring) are solid and TDD-evidenced, but the bench's core premise is weakened by an unrealistic diff shape (issue 2) and a `GLOBAL_CONSTRAINTS` gap (issue 3) that together bear on 8 of 9 cases, plus a demonstrated false-positive regex (issue 1) that invalidates 2 of 9 cases outright; these should be fixed before task 04 treats bench output as a ship gate.
