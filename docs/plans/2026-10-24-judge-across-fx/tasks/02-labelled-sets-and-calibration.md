# 02: Labelled sets and calibration

**Status:** ready-for-agent
**Blocked by:** 01
**Phase:** MVP

**What to build:** every new judge question has a labelled set big enough to support its bar, has been scored once on the owner's configured judge, and the scores decide what may act. Six JSON sets go into this plan's `sets/` directory, including labelled items for every catalogue edit rule that task 09 ships. `scripts/judge-calibrate.js` (task 01) scores each set and measures whether the judge serves concurrent requests; the printed rows go into `scores.md`. From those rows `src/lib/judge-features.ts` commits, per feature, `enabled` only where the score cleared its bar and `log-only` everywhere else; the list of catalogue rules that may refuse an edit (each cleared the refusal bar on its own items); and whether one edit's rule requests go out together or one at a time. A gate test ties all three to `scores.md`, so no value can drift from its measurement.

**Labelled set shapes** (each file is a JSON array; write U+2013 and U+2014 only as the JSON escapes `\u2013` and `\u2014`, so no file carries a dash character; secrets are fake values only, such as `AKIAIOSFODNN7EXAMPLE`; dangerous command strings appear only as data; no entry is ever run):
- `lane-hint.json`: `{ "prompt": string, "lane": string }`, at least 60 entries; `lane` is a lane in `KIND_LANES`. It holds the 17 prompts of `tests/lane-triggering/prompts/` verbatim, each labelled by its file name before `__` (`none__*` is `none`), at least 3 entries for every lane in `KIND_LANES`, and at least 10 `none` entries that are plain questions about code (the class that must cost one request).
- `dispatch-sizing.json`: `{ "subagent_type": string, "description": string, "prompt": string, "kind": DispatchKind }`, at least 50 entries: at least 15 `lookup` and 15 `small-edit` (the `lower` label), at least 4 of each other kind.
- `edit-rules.json`: `{ "id": string, "rule": string, "scope": "line" | "file", "path": string, "added": string, "file"?: string, "breach": boolean }`, covering every catalogue rule task 09 ships, with at least 30 breaches and 10 clean entries per rule. Built-in rules have no entries: they are checked in code (task 07). `file` is present exactly on `scope: "file"` entries and holds the whole post-edit file. The rule texts, copied verbatim from task 09's catalogue (task 09's gate ties the two):
  - `rails-fk-index`, scope `file`: `Every foreign key column a migration adds also gets an index.`; its clean entries include at least 3 whose `add_index` sits in the file outside the added lines.
  - `rails-no-rescue-nil`, scope `line`: `No rescue nil, and no rescue clause whose body is empty.`
  - `dotnet-no-blocking-async`, scope `line`: `No .Result or .Wait() on a Task inside async code.`
  - `dotnet-no-empty-catch`, scope `line`: `No catch block whose body is empty.`
  - `react-no-raw-html`, scope `line`: `No dangerouslySetInnerHTML with a value built from user input.`
  - `react-key-not-index`, scope `line`: `A list rendered with map gives each item a key that is not the array index.`
  - `docker-pinned-base`, scope `line`: `Every FROM line pins a version tag or digest, never latest or no tag.`
  - `web-img-alt`, scope `line`: `Every img element has an alt attribute.`
- `review-tripwires.json`: `{ "lens": "fx-lens-security" | "fx-lens-database" | "fx-lens-silent-failure", "change": string, "hit": boolean }`, 20 per lens (10 hits, 10 misses); `change` is unified-diff text under `REVIEW_CHUNK_CHARS`.
- `review-authored.json`: `{ "path": string, "head": string, "label": "authored" | "generated" }`, at least 30 entries, 15 of each, generated ones drawn from `rails new`, `create-react-app`, `dotnet new`, lock files and compiled output.
- `review-search.json`: `{ "lens": string, "path": string, "function": string | null, "text": string, "flag": boolean }`, at least 20 entries for each of the five lenses, at least 8 flagged per lens, in at least 5 of the 13 language families of design story 16.

**Seam:** the set files through `parseLabelledSet` and the `judge-sets` gate; `FEATURE_GATE`, `REFUSING_RULES` and `JUDGE_CONCURRENCY` against `scores.md` through `judge-features.test`.

**Tests:**
- Each committed set file parses with `parseLabelledSet` for its feature and meets every minimum count above (per lane, per kind, per rule, per lens, per label).
- `lane-hint.json` holds every prompt text of `tests/lane-triggering/prompts/*.txt`, labelled as above.
- `edit-rules.json`: the set of ids is exactly the eight catalogue ids above; every entry's `rule` equals the text listed for its id; `file` is present exactly when `scope` is `file`; no entry's id is `no-dashes`, `no-secrets` or `no-conflict-markers`.
- No committed set file contains the bytes of U+2013 or U+2014.
- `FEATURE_GATE` has exactly the six `JudgeFeature` keys, and each value equals the gate column of that feature's row in `scores.md` (a feature whose row reads `not measured` must be `log-only`).
- `REFUSING_RULES` equals, in order, the ids of the `| rule <id> |` rows in `scores.md` whose last column is `refuses`; it is `[]` when the `edit-rules` feature row is `log-only` or `not measured`.
- `JUDGE_CONCURRENCY` equals the mode column of the `| concurrency |` row in `scores.md`, and is `sequential` when that row reads `not measured`.
- `scores.md` holds a `Backend:` line and a `Measured: 2026-10-` line.

**Risks:** a labelled set written from the same mental model as the questions overstates accuracy: draw lane prompts from the lane-triggering set and real requests in `docs/plans/*/state.md`, draw rule items from real code in the stacks named, and write every set before looking at any judge answer. A judge that is not running, or one that cannot answer a feature, leaves that feature `log-only`: write the row `| <feature> | not measured | | | | | log-only | | |` (and `| concurrency | not measured | | | |`), which is the intended result. A judge whose server serves one request at a time measures `sequential`; one launched with several slots may measure `concurrent`: the measurement decides, not the server's settings.

**Idempotency:** `judge-calibrate` writes nothing; rerunning it prints new rows, and only a deliberate edit of `scores.md` and the three constants changes what ships.

**Testing:** offline gates over the sets and the constants; one live calibration per feature, plus the concurrency run, on the owner's configured judge, recorded in `scores.md`.
