# 07: Edit rules on Claude Code and Codex

**Status:** ready-for-agent
**Blocked by:** 02, 03
**Phase:** Core

**What to build:** before a file write or edit lands on Claude Code (`Write`, `Edit`, `MultiEdit`, `NotebookEdit`) or Codex (`apply_patch`, and a shell-run `apply_patch`), fx checks the lines the edit adds against the rules that apply to that file. A `Write` is compared with the file on disk, so only lines it adds are checked; an `Edit` or `MultiEdit` contributes the lines its new strings add over its old strings. fx ships three built-in rules that hold in every repository and are checked in plain code, with or without a judge: no em or en dashes in Markdown, no merge-conflict marker lines, and no secret the fx redactor recognises. A built-in breach refuses the edit with `[fx] rule <id>: <rule> (<file>)`. A repository adds its own rules under `.fx.json` `rules`, each `{ id, glob, rule }` with an optional `scope: "file"`; those go to the judge, one yes/no question per matching rule, two per request, over the added lines and, for a file-scope rule, the whole post-edit file, capped. Only a rule that cleared the refusal bar on its own labelled items (task 02's `REFUSING_RULES`) may refuse; every other judged rule only advises, with one context line, even on a confident breach. An unsure answer advises; no judge, a failed call, the gate at `log-only` or the switch `hooks.edit_rules: false` lets the edit through silently. One edit's judge requests go out together or one at a time as task 02 measured, all inside one per-edit deadline, and count toward the features' breaker, never the shell guard's. There is no stamp or override: the owner changes the rule list instead. Runs after the existing fx-state refusal and the lane check, which keep their fail-closed and fail-open behaviour; a crash in the rule check allows the edit.

The agent can write `.fx.json` (fx-setup runs as the agent), so a rule or switch can change mid-session. The health line and the Stop check print a one-line notice when the `rules` or `hooks` of the top-level `.fx.json` changed during the session; ADR 0048 records the remaining gap (task 13).

**Risks:** a wrong refusal blocks real work: built-ins refuse only on exact code checks, a judged rule refuses only when its own labelled items cleared 95% precision with at most 10% unsure answers on clean items (task 02), every other judged rule advises, and the switch turns all of it off. A `Write` that rewrites a file with old breaches is judged on its new lines only, so old breaches never block it; a file-scope rule does see old breaches, which is why only measured rules refuse. The redactor decides `no-secrets`, so a redactor false positive (a fake key in a test fixture) refuses; `hooks.edit_rules: false` is the way out, and the redactor's own test table is its measurement. The judge reads at most 2,000 characters of added lines and 4,000 of the file; the log line's `text` names the file. Rule text comes from `.fx.json`, which the agent can write: the parser caps it, an unmeasured rule can only advise, and the notice tells the owner when it changed.

**Testing:** unit tests for glob, rule matching, added lines, built-in checks, patch additions, changed files, the notice and the parser; process tests on all three hooks with the fake server; the existing hook gates as regression.
