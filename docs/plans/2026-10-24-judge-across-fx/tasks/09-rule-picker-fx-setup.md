# 09: Rule picker in /fx-setup

**Status:** ready-for-agent
**Blocked by:** 02, 07
**Phase:** Core

**What to build:** a repository owner running `/fx-setup` is offered edit rules suited to the repository's stacks and picks the ones that apply, without ever hand-editing a rule list. fx ships a catalogue of rules per stack (`rails`, `dotnet`, `react`, `docker`, `web`, the stack names `references/stacks/` already uses). The setup lane reads the stacks it has just written to `.fx.json`, runs `node "<FX>/lib/judge-cli.js" rules <stack>...` to get the candidates as JSON, asks the owner which apply through the host's question tool, and writes exactly the picked rules to `.fx.json` `rules`. It tells the owner that fx's three built-in rules apply everywhere and need no judge, that the picked rules run only with a judge configured, that a picked rule refuses an edit only if it was measured on its own labelled items and otherwise only advises, and that `hooks.edit_rules: false` turns them all off. Rules are read from the git top level as `.fx.json` is today; only this run writes them.

  - `RULE_CATALOGUE: Record<string, EditRule[]>`, exactly:
    - `rails`: `{ id: 'rails-fk-index', glob: 'db/migrate/**/*.rb', rule: 'Every foreign key column a migration adds also gets an index.', scope: 'file' }`, `{ id: 'rails-no-rescue-nil', glob: 'app/**/*.rb', rule: 'No rescue nil, and no rescue clause whose body is empty.' }`
    - `dotnet`: `{ id: 'dotnet-no-blocking-async', glob: '**/*.cs', rule: 'No .Result or .Wait() on a Task inside async code.' }`, `{ id: 'dotnet-no-empty-catch', glob: '**/*.cs', rule: 'No catch block whose body is empty.' }`
    - `react`: `{ id: 'react-no-raw-html', glob: '**/*.{jsx,tsx}', rule: 'No dangerouslySetInnerHTML with a value built from user input.' }`, `{ id: 'react-key-not-index', glob: '**/*.{jsx,tsx}', rule: 'A list rendered with map gives each item a key that is not the array index.' }`
    - `docker`: `{ id: 'docker-pinned-base', glob: '**/Dockerfile*', rule: 'Every FROM line pins a version tag or digest, never latest or no tag.' }`
    - `web`: `{ id: 'web-img-alt', glob: '**/*.{html,erb,jsx,tsx,vue}', rule: 'Every img element has an alt attribute.' }`
  - `catalogueFor(stacks: string[]): EditRule[]`: the entries for each known stack in the given order, each id once; unknown stacks add nothing.
- Produces `node lib/judge-cli.js rules [<stack>...]`: prints `JSON.stringify(catalogueFor(stacks), null, 2)` and a newline to stdout, exit 0. The usage line becomes `usage: judge-cli path|check|rules [<stack>...]|write --base-url <url> --model <id> [--api-key-stdin | --api-key-env <NAME>] [--insecure-http]`.
- `commands/fx-setup.md` section 8 says, in this order: the three built-in rules by id, that they apply in every repository and are checked without a judge; that the picked rules run only when a judge is configured (section 7), that a confident breach refuses the edit only for a rule measured on its own labelled items (ADR 0048 lists them), and that every other picked rule only advises; run `node "<FX>/lib/judge-cli.js" rules <the stacks in .fx.json>`; an empty array means skip the section; otherwise ask through the host's question tool, several choices allowed, at most 4 rules per question (more questions for more rules), each option labelled with the rule's id and its sentence, "None" first; write the picked rules to `.fx.json` `rules` exactly as printed, appended after any rules already there with a different id; the sentence `Never write a rule the owner did not pick, and never edit a rule's text.`; and that `"hooks": { "edit_rules": false }` turns every rule off for the repository. The Report section gains the line `- Edit rules: <ids written, or none>`.

**Seam:** `rule-catalogue` directly; `lib/judge-cli.js` as a process; `commands/fx-setup.md` and `skills/fx-setup/SKILL.md` as text.

- The ids of `RULE_CATALOGUE` are exactly the ids in `sets/edit-rules.json`; for each, the catalogue's `rule` equals every set entry's `rule` for that id, and `scope: 'file'` in the catalogue matches `scope: "file"` in the set.
- Every id in `REFUSING_RULES` is a `RULE_CATALOGUE` id.
- `catalogueFor(['rails', 'docker'])` ids `['rails-fk-index', 'rails-no-rescue-nil', 'docker-pinned-base']`; `catalogueFor(['rails', 'rails'])` ids `['rails-fk-index', 'rails-no-rescue-nil']`; `catalogueFor(['elixir'])` is `[]`.

**Risks:** a catalogue rule the judge reads badly could refuse good edits in every repository that picks it: each catalogue sentence is one checkable fact, only a rule in `REFUSING_RULES` (95% precision on its own labelled items, task 02) can refuse, and the rest only advise. A catalogue text edited after task 02 measured it would ship unmeasured: the set tie above fails the build. The setup lane writes `.fx.json`; it must merge into the existing file, never replace it: the section says to append.

**Testing:** unit tests for the catalogue, a process test for the CLI, a text gate for the lane.
