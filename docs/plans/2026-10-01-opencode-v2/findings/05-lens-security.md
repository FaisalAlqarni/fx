1. [Important] /development/fx/.worktrees/opencode-v2/plugins/fx-opencode-v2.js:44, :117, :129: the recorded-command map is shared across the whole process and keyed only by the tool call id. Nothing scopes it by session or message. OpenCode takes that id from the provider unchanged. It removes duplicate ids only within a single Gemini stream (`core/src/.../ai/src/protocols/gemini.ts:742-749`, whose comment warns about "cross-request collisions in downstream registries"). The OpenAI-compatible path passes the provider's id straight through (`ai/src/protocols/openai-chat.ts:1122`). Here is how two concurrent shell calls that share an id play out:
   - Call B records `git -C . reset --hard`.
   - Call A records `ls`, which overwrites B's entry.
   - B's evaluate reads `ls` and allows it.

   Several async steps sit between execute.before and evaluate (`tool/plugin/shell.ts:122-133`), so this interleaving can happen. The attacker gets a guarded command run uninspected. Using a spelling the policy layer does not cover (`-C`, `-c`) also gets it past the backstop. Fx dispatches subagents in parallel, so the concurrency is routine. What stays unverified is whether a provider the user runs actually repeats ids. The same key collision is built into CodeMode: children of one CodeMode call share its id (`tool/plugin/shell.ts:233` comment, `codemode/tool.ts:95`). That is latent only because the shell tool is registered with `codemode: false` (`tool/plugin/shell.ts:192`), and any plugin can change that option.

2. [Important] /development/fx/.worktrees/opencode-v2/plugins/fx-opencode-v2.js:117: the guard checks the command as it stood when fx's execute.before hook ran, not the command that gets spawned. Hooks run in the order they were registered (`core/src/plugin/hooks.ts:88-95`). Any tool execute.before hook registered after fx can still replace `event.input`. Every plugin's `shell` `create.before` hook runs after that and can rewrite `invocation.command` before the permission check (`core/src/shell.ts:274-275`). OpenCode's parser and the policy layer see the rewritten text, while fx inspects the original. A plugin that expands aliases or wraps commands can turn text the guard allowed into a destructive git command, and fx never sees it. This needs a second plugin, and plugins are trusted code, so it is a gap between check and use rather than a live exploit.

3. [Minor] /development/fx/.worktrees/opencode-v2/plugins/fx-opencode-v2.js:129-135: one error path lets the command through. If `ev.source` is `null` (or any falsy value other than `undefined`), then `command` becomes `null`, the `=== undefined` check does not fire, and `inspect(null)` returns allow (`lib/git-guard.js:225`). Today every shell evaluation builds a real source object (`tool/plugin/shell.ts:117-121`), so this cannot happen now. It is the one error path in the shell branch that does not deny. Every other path does deny: a failed load, a missing entry, an `inspect` that throws, and a malformed verdict.

When the id does not collide, the alias case denies, so it costs availability but lets nothing through.
