1. [Important] /development/fx/.worktrees/opencode-v2/plugins/fx-opencode-v2.js:204-210: the grant is wider than ADR-0026 in one case. If the user narrowed `subagent` on `general` to certain resources, fx still allows every other resource. Line 207 removes the earlier `subagent` rules and line 208 pushes `{subagent, *, allow}`. The user's opencode.json rules are still appended after this, and `Permission.evaluate` takes the last matching rule (core/src/permission.ts:87-97), so a user rule that matches the resource wins. A narrow one does not. Take a user rule `{action:'subagent', resource:'explore', effect:'allow'}`. It answers only for `explore`. A dispatch of `general` or any `fx-*` agent falls through to fx's `*` allow, where it used to hit the built-in deny. The 1.x guard skips the grant whenever any `task` key exists, so there a narrow rule is the user's whole answer. Here it is not. What an attacker gets: a prompt-injected `general` can dispatch agents the user's allow-list left out, down to the depth `experimental.subagent_depth` allows. It cannot dispatch primary agents (core/src/tool/plugin/subagent.ts:136). No gate test covers this case.

Your four questions, checked against the v2 source:

- **ADR-0026 ordering:** it holds apart from finding 1. `ConfigAgentPlugin` is in the `post` list (core/src/plugin/internal.ts:252-269). Plugins load one at a time, in order (core/src/plugin.ts:127-170), and transforms run in the order they registered (core/src/state.ts:19). So a user's global `*` or `subagent` rule (core/src/config/plugin/agent.ts:91) and the user's own `general` permissions (line 122) land after fx's allow, and the user's answer wins. The filter at fx line 207 only removes rules that built-ins or plugins loaded before fx put there, never the user's config rules.
- **The six read-only agents:** the grant touches only `general`. It does not apply to the read-only agents; see finding 2.
- **Can a denial message turn a deny into an allow:** no. `deny()` sets `ev.effect = 'deny'` before it builds the message (fx line 82), and line 132 comes before line 133. If building the message threw, the effect would already be `deny`, and nothing later in the hook sets it back to `allow`. An earlier deny returns before the hook runs at all (permission.ts:175).
- **The git guard:** it still fails closed. `guardError` throws into the catch and is denied (fx lines 106, 120-122). A missing call key or command text is denied (109-111).
